## Последнее обновление

Критические операции платежей и склада перенесены в серверные транзакции Supabase:

- добавлен SQL-файл `supabase/transactional-payments-inventory.sql`;
- добавление платежа, полная оплата и возврат блокируют строку заказа, повторно считают оплату из таблицы платежей и атомарно обновляют остаток;
- поступление, резервирование, списание и снятие резерва блокируют материал или резерв и не допускают одновременного перерасхода;
- повтор одной операции с тем же UUID возвращает ранее сохраненный результат и не создает дубль;
- прямое изменение критических таблиц из роли `authenticated` отозвано; клиент вызывает только разрешенные RPC-функции от текущей сессии сотрудника;
- итог оплаты заказа дополнительно защищен серверным триггером и не может быть перезаписан устаревшим локальным состоянием;
- в `staff_action_log` сохраняются сотрудник из `auth.uid()`, время, действие, объект, заказ и состояния до/после;
- в настройках добавлена вкладка `Журнал действий` с автоматическим обновлением через Supabase Realtime;
- предоплата при создании и корректировка оплаты при редактировании заказа проходят через ту же платежную транзакцию;
- кнопки платежей и склада блокируются на время запроса, а локальный кеш после ответа обновляется из общей базы без обратной отправки снимка;
- роли и права доступа не изменялись;
- `service_role` не используется в клиентском коде и не требуется для транзакционных операций.

После проверки в двух браузерах устранен откат полной оплаты:

- при настроенном Supabase критические операции больше не могут переключиться на локальное сохранение из-за отсутствующего браузерного флага синхронизации;
- локальный fallback оставлен только для разработки без настроенного Supabase;
- после серверного конфликта второй браузер сначала перечитывает актуальный снимок базы, а затем показывает сообщение;
- карточка заказа, финансы и склад обновляют экран как после успеха, так и после отклоненной конкурентной операции;
- добавлены регрессионные тесты выбора серверного режима и обновления кеша после RPC-ошибки.

## Единая структура данных

Основные сущности связаны через id:

- клиент: `client.id`
- заказ: `order.clientId`
- платеж: `payment.orderId`, `payment.clientId`
- производство: `productionTask.orderId`
- установка: `installationTask.orderId`
- документ: `document.orderId`, `document.clientId`

Один и тот же заказ должен отображаться в списке заказов, карточке заказа, карточке клиента, финансах, производстве, установке и документах.

## Сохранение нового заказа

На странице `/orders/new` кнопка `Создать заказ` должна:

1. Проверить обязательные поля.
2. Найти клиента по телефону или создать нового.
3. Сгенерировать номер заказа вида `ЗК-2026-0143`.
4. Создать заказ в localStorage.
5. Создать позиции комплектации и услуги внутри заказа.
6. Если есть предоплата, создать платеж.
7. Создать задачу производства со статусом `Ожидает макет`.
8. Создать задачу установки со статусом `Не назначена`.
9. Перенаправить пользователя на `/orders/[id]`.

Новый заказ должен появляться в:

- `/orders`
- `/orders/[id]`
- `/clients`
- `/clients/[id]`
- `/finance`
- `/production`
- `/installation`

## Общая база и синхронизация

- Сотрудники входят через Supabase Auth.
- Активность сотрудника проверяется через `staff_profiles`.
- После входа CRM загружает общие данные из Supabase.
- Изменения отправляются точечно: только измененные или удаленные записи.
- Другие открытые браузеры получают изменения через Supabase Realtime.
- Если Realtime недоступен, работает фоновая проверка без ручного `F5`.
- Ручные кнопки переноса и загрузки данных удалены.
- Итоги оплаты пересчитываются из общего списка платежей при загрузке.
